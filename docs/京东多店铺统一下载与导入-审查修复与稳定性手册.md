# 京东多店铺统一下载与导入：审查、修复与稳定性手册

## 1. 适用范围

本手册适用于以下三个流程合并后的多店铺链路：

1. 京东店铺商品 SKU 主数据下载与导入；
2. 京东商智商品明细 SKU 分天下载与导入；
3. 京东商智商品明细 SPU 分天下载与导入。

统一入口为 `tools/jd-multi-store-runner.ts`。店铺配置来自 `config/jd-store-accounts.json`，但注册表只能保存非敏感信息，严禁保存密码、Cookie、Token、验证码或登录态。

## 2. 正确完成的定义

“下载成功”不等于“流程完成”。单个步骤只有同时满足以下条件才能标记为 `completed`：

- 文件已落盘，且不是 `.crdownload`；
- 工作簿维度、标识列和完整日期覆盖验证通过；
- 文件已提交到运营管理系统；
- API 返回唯一、结构完整的导入结果；
- `imported` 对应 HTTP 201，`duplicate` 对应 HTTP 200；
- 批次状态为 `completed`、警告数为 0；
- source、dataset、platform、shopName 和目标日期全部匹配当前步骤。

每日完整工作流在创建京东日数据任务前，必须先按四店分别查询 SKU、SPU 在“上海昨天所在月 1 日至昨天”范围内的权威落库覆盖。覆盖响应必须未截断，且实际日期与缺失日期构成完整、互斥的自然日集合；否则 A 失败关闭。连续缺口可以合并为一个下载区间，离散缺口不得跨过已有日期合并。商品 SKU 主数据不按缺口判断，四店仍每天各更新一次；SKU/SPU 没有缺口的维度不创建下载任务。C 在逐个复核缺口批次后，必须重新查询四店两维度的整个扫描范围并确认缺口为零。

统一 runner 只接受子进程输出的一行 `@@JD_PIPELINE_RESULT@@<JSON>`。普通日志或尾随遥测 JSON 不得作为成功依据。

每小时安全重试模板采用后，只对定时 execution 或上一轮自动重试的可重试失败生效：等待 60 分钟后，从原工作流创建新的完整 execution，重新领取共享 helper，并重新经过 A/B/C 和所有身份、恢复清单、幂等及落库回查门禁。验证码、安全验证、业务码 601、凭据/登录失效、店铺身份不符、跨店、任务歧义、来源日期未开放、owner 冲突以及任何点击/提交结果未决均停止自动重试并转人工。不得将其改成失败节点重放。统一结构与受控发布顺序见 [`N8N_HOURLY_SAFE_RETRY.md`](N8N_HOURLY_SAFE_RETRY.md)。

## 3. 本次运行暴露的坑与根因

| 坑 | 根因 | 修复原则 | 必须保留的反例 |
|---|---|---|---|
| SKU 后运行 SPU 时无法识别新任务 | 下载中心异步加载，首帧空表被当作 baseline；任务标题又不含维度 | baseline 必须稳定，首帧空数据无效；按 manifest 精确接管 | `[空, 空, 旧任务, 旧任务]` 不得提前返回空 baseline |
| 下载完成却被总流程标记成功 | runner 只看退出码和任意 JSON，没有验证导入批次 | 只接受唯一哨兵和完整 `importResult` | code 0 但只有 `savedPath` 必须失败 |
| 日数据需要人工 FormData 导入 | 商智脚本只下载，没有闭环导入 | 下载后自动调用正式导入接口并验证批次 | API 500、错店、错日期、错 dataset 都必须失败 |
| 缺中间某天仍通过 | 只检查最小/最大日期或维度 | 枚举目标区间的每个自然日，检查缺失和越界 | 1 日、3 日存在但 2 日缺失必须拒绝 |
| 两店导入同一文件互相覆盖 | 批次唯一键和主数据行键没有店铺作用域 | 批次与行键都包含 platform、shopName | A/B 店同 hash 共存；同店重复仍幂等 |
| 店铺主数据恢复清单串店 | 所有店共享 `active-task.json` | 活动清单文件名包含 `storeKey` | 两个 storeKey 路径必须不同 |
| 登录失效要等 30 秒 | 先等待业务 UI，后识别登录页 | 对明确 passport/login 状态快速失败 | “账号中心 页面加载中”不得误判为登录页 |
| n8n 与系统服务刚恢复时静默商品主数据偶发在启动前失败 | 首个 Win32 窗口守护进程需要即时编译互操作类型，原 5 秒就绪预算在冷启动高负载下过短 | 守护就绪预算固定为 15 秒；超时仍关闭本轮 Chromium 并失败关闭，不放宽窗口隐藏或执行所有权门禁 | 守护未输出 `READY` 时不得继续导航；已就绪时仍必须绑定实际 browser PID 持续隐藏窗口 |
| 业务 URL 首帧空白时误报已有登录态 | 京东先显示业务 URL，随后才重定向 passport；旧守护把“当前不是登录页”直接当成已认证 | 把页面分类为 `authenticated/login/pending`；只有受控业务 UI 才能成功，空白/加载中状态有界等待，延迟登录重定向必须进入登录处理 | 第一次采样为无内容的 `jdsz.jd.com`，第二次跳到 `passport.jd.com` 时必须返回 login；pending 超时必须失败关闭 |
| 人工可正常登录但自动守护报密码表单未就绪 | 新版商家登录页把“账号密码登录”绑定在唯一外层 `div.tabs__item.tabs__item-click`，旧守护只查按钮、链接和 ARIA 控件；页面顶部的语言控件还是一个可见 `text` 输入，旧版宽泛候选会把它误算为第二个账号框 | 只接受标签精确且全页面唯一的已知外层模式控件，单击一次后再等待带明确账号语义的唯一账号密码表单；不再用任意 `input[type=text]` 兜底；表单等待保持 20 秒有界 | 外层 div 与子 span 同文案时只能点击外层一次；语言输入不得被填写；多个账号语义候选、多个外层候选、验证码或最终多表单仍必须在读取凭据前失败关闭 |
| 商品明细日期控件偶发被体验评分弹层挡住 | `#ux-scene-research` 可能在进入日期选择并完成首次观察后才延迟挂载，Playwright 对原控件点击因 pointer interception 超时 | 仅当错误同时包含 `ux-scene-research` 和 `intercepts pointer events` 时，重新按完整文案与唯一“我不愿作答”退出项核验并关闭，再把原可逆日期菜单动作重试一次 | 普通页头、广告或未知弹层不得触发恢复；第二次点击失败必须原样失败关闭；下载任务尚未创建才可从该段续接 |
| 注册表可以共享浏览器目录 | 没校验 profile、端口、下载目录的解析后唯一性 | 加载注册表时 fail closed | 大小写或相对路径归一后碰撞必须拒绝 |
| 每月 1 日导入成功后被 runner 拒绝 | runner 用今天的月初，子流程用昨天所在月月初 | 默认区间统一为昨天所在月份月初至昨天 | 7 月 1 日必须得到 6 月 1 日至 6 月 30 日 |
| 慢页面提交后无法恢复 | manifest 的 createdAt 在页面准备前生成 | 在确认点击前即时生成并原子写盘 | 页面准备超过两分钟仍应以确认时间恢复 |
| 非标准 HTTP 也被当作成功 | 客户端只检查 `response.ok` | HTTP 与 payload status 精确对应 | 200/202 imported、201/202 duplicate 必须拒绝 |
| 审计写“已提交”但京东没有新任务 | 把浏览器 `click()` 返回误当作远端任务创建 | 先记录 `task_click_invoked`，只在唯一 post-baseline 任务行出现后记录已创建 | click 返回但任务表不变时不得写 taskId 或“已创建” |
| 创建接口仍在执行时提前刷新，业务拒绝又被页面吞掉 | Playwright 点击完成不等于异步 `createExportJob` 完成；京东组件 `catch` 不展示持久错误 | 点击前监听精确创建请求，校验 HTTP 200 与业务码 200 后才刷新任务表；拒绝原因有界写入审计 | HTTP 200 但业务码非 200、无创建请求、创建响应未完成时均不得开始轮询或再次点击 |
| 页面已有商品但导出仍报“总行数必须大于0” | 导出抽屉在商品查询稳定前打开并永久捕获 `total=0` | 关闭旧抽屉，触发唯一商品查询，核对接口与页面同一正数总行数后再打开；明确“创建导出任务失败”时归档无 taskId 清单并允许修复后立即重试 | 页面显示 83 条但旧抽屉总数为 0 时不得提交；明确失败不得再隔离等待 30 分钟 |
| 关闭抽屉后“查询”按钮可见却点不到 | 京东固定顶部栏遮挡按钮鼠标坐标 | 只对唯一绑定的可逆查询按钮发送一次 DOM click，并继续校验唯一查询响应和页面正数总行数 | 坐标被遮挡时不得重复鼠标点击；缺少响应或总数不一致仍失败关闭 |
| 切店后查询入口首次采样为空 | 京东商品列表按店铺异步渲染速度不同 | 在零入口状态下有界等待；唯一入口成立才查询，多个入口立即失败关闭 | 慢店铺不得因一次空采样失败；歧义入口不得靠等待或点击消解 |
| 页面级查询按钮先于筛选容器出现 | 京东慢店铺分阶段渲染 DOM | 唯一未绑定按钮只允许有界等待且不得点击；容器一一绑定后才继续 | 半渲染状态不应立即失败，多个按钮或最终未绑定必须拒绝 |
| 页面显示“批量操作”但导出菜单未展开 | 控件文字有尾随空格，内层按钮用于稳定身份，新版下拉展开事件绑定到外层 `span.batch-dropdown-link`，部分账号只响应键盘契约 | 用唯一内层 `<button>` 和首尾空白标签确认身份，先点击包含该按钮的唯一外层触发器；3 秒内未展开且同一触发器仍唯一、仍收起时，只补一次 Enter，并排除“更多批量工具” | 点击与单次 Enter 均不得触发查询或导出业务动作；展开后必须连续稳定出现唯一“导出查询商品”，多个触发器必须拒绝 |
| “导出查询商品”已出现，但点击时因页面重绘脱离 DOM，随后一直等待入口 | 京东重绘会同时替换入口并收起短时“批量操作”菜单；只等待旧菜单项不会重新出现 | 仅在确认错误为 `detached from the DOM` 或 `element is not stable` 时，再执行一次同一受控菜单展开流程；复用本轮查询状态栅栏，禁止补点“查询” | 第二次仍须核验唯一外层“批量操作”和连续稳定的唯一导出入口；最多重试一次，其他点击错误立即失败关闭，不得创建重复任务 |
| 文档导致所有店导入第一店 | 示例把 shopName 写死 | 始终使用所选注册表项的 `shopName` | 文档和 Skill 不出现固定第一店作为通用参数 |
| 商智用第一店清单在第四店创建任务 | 独立 profile 中的商智登录身份被人工切换，但提交前只信任注册表参数，没有读取页头店铺 | 恢复、baseline、确认和下载前精确核验页头唯一商城链接中的 `shopName + shopId`；manifest 同时绑定 `storeKey + shopName + shopId` | 期望 `701455` 而页头/任务为 `711743` 时，确认与下载点击次数都必须为 0，错误清单只归档不接管 |
| 商智公告点了关闭仍超时 | 公告在主页面可交互后延迟挂载，关闭控件先渲染、后完成事件绑定；旧代码首次可见即点击 | 等待同一公告图片身份和唯一安全关闭控件连续稳定；首击无效只允许重新核验同一公告后再试一次 | 关闭控件从 0→1 时不得抢点；第二个公告、多个弹层或多个关闭控件不得自动连续关闭 |
| 凌晨运行选择不了昨天 | 上海日期已跨日，但京东数据开放上限仍停在前一天 | disabled 结束日按 source-not-ready 失败关闭，保留审计等待 10:00 调度续跑 | 目标 8 月 11 日禁用时不得降级到 8 月 10 日或反复点击 |

## 4. 多店铺隔离规则

### 4.1 注册表

每个启用店铺必须拥有唯一的：

- `storeKey`：只允许小写字母、数字和连字符；
- `shopId`：只允许数字；
- `browser.executablePath`：受控 Chromium 可执行文件；
- `browser.userDataDir` 与 `browser.profileName`；
- `browser.profileDir`；
- `browser.debugPort`；
- `browser.downloadDir`。

路径必须在解析成绝对路径、统一大小写后再比较。账号密码不得进入注册表、n8n、环境变量、命令参数、日志或审计；只有显式配置 `loginMode=windows_dpapi_credentials` 的店铺可以使用当前 Windows 用户绑定、Git 已忽略的 DPAPI 密文。凭据只在内存中解密并最多提交一次，不回读字段值，不跨店复用。

### 4.2 浏览器与执行顺序

一个店铺使用一个独立 Chromium profile；允许四店共享同一 Chromium 用户数据根目录，但 `profileName` 与实际 `profileDir` 必须唯一，且只能由受控 runner 严格串行启动。商品主数据、商智 SKU/SPU 和市场榜单共用一个校验活进程身份的全局 Chromium 所有权锁。商品主数据页面日常使用普通有头 Chromium，不使用 `HeadlessChrome`；严格静默模式先把窗口放到屏幕外，再由绑定 CDP 实际 browser PID 的 Win32 守护持续隐藏顶层窗口，不能只依赖 `--start-minimized`，也不得复用未受本轮守护的既有进程。自动运行从空白页启动，在唯一受控页面导航前监听首屏商品查询，必须以该响应和页面正数总行数的精确回显作为后续导出的新鲜度证据，禁止重复打开商品页或在首屏查询后再补点。商智 SKU/SPU 分天仍可使用 `headless=new`；每个自动阶段只关闭自己启动的 Chromium，确认调试端口释放后才能进入下一阶段或切店。商品主数据步骤发现同端口残留旧 `HeadlessChrome` 时先关闭旧实例再启动后台有头实例，端口被并发接管则失败关闭。普通流程在登录失效、验证码、安全验证、业务码 `601` 或店铺登录身份异常时才关闭后台实例并打开当前店铺对应的可见 Chromium profile；静默副本把 `silentNoWindow=true` 固化进多店与市场榜单计划和 runner 审计，并向三个子流程传递 `--no-visible-recovery`，同类异常只失败关闭、保留 manifest/审计，不打开窗口。两种模式都绝不因异常自动重放远端任务或下载点击；`601` 不能仅按浏览器模式、CDP 或点击方式作单因归因，也不得通过反检测或系统注入点击绕过。首次登录使用显式 `--interactive-login`。所有店铺严格串行运行：当前店铺的主数据、SKU 日数据、SPU 日数据完成后，才能切换下一店铺。任一步失败立即停止并保留审计，不使用 `Promise.all` 并发四店。

登录守护不能用一次 URL 采样判断认证成功。京东可能先载入空白业务 URL，再延迟跳转到 passport；程序必须有界等待并区分三种状态：受控业务 UI 为 `authenticated`，明确 passport/login 页面为 `login`，空白、加载中或无法识别为 `pending`。`pending` 超时必须失败关闭。进入 `login` 后，仅当页面存在唯一账号密码表单、无验证码/安全验证、当前店铺启用 DPAPI 且执行所有权匹配时，才可在内存中解密并提交一次；提交后仍须等到受控业务 UI 才能成功。URL 离开登录页、密码框暂时消失或 HTTP 导航完成均不是成功证据。

商智登录态可能在同一 profile 内被人工切换，因此“端口和 profile 正确”不等于“店铺身份正确”。程序必须从页头唯一的 `mall.jd.com/index-<shopId>.html` 店铺链接读取实际 `shopId` 与可见店铺名，并在恢复 manifest、建立下载中心 baseline、确认创建远端任务、进入下载中心以及点击下载前分别核验。缺失、歧义或与注册表不一致时均视为交互异常：关闭后台实例并显示该注册店铺对应的 Chromium profile，原步骤失败关闭，不自动重放。

商品明细公告只允许关闭唯一含“公告图片”的弹层。由于弹层和事件绑定均可能延迟，程序先等待同一图片身份下的唯一安全关闭控件连续稳定，再点击一次；若仍可见，只能在公告身份未变且关闭控件仍唯一时重试一次。弹层或图片身份变化时停止，不能顺手关闭后续未知公告。

默认缺口扫描范围始终是上海时区“昨天所在月 1 日至昨天”。A 先读取四店 SKU/SPU 的该范围落库覆盖，只把连续缺口区间交给下载步骤；商品主数据仍每日更新。凌晨京东尚未开放某个计划缺口的结束日时，结束日日历单元格会是 disabled；这是来源尚未就绪，不是允许缩短范围的信号。步骤必须失败关闭并保留 runner 审计，待来源开放后续跑；不得改成前一天并伪报完整覆盖。

### 4.3 数据库身份

批次唯一身份为：

```text
source + platform + shopName + fileHash
```

商品主数据行键也必须包含 platform 和 shopName。升级旧库时，需要移除历史 `UNIQUE(source,file_hash)`，保留所有旧列和数据，并建立新的四列唯一约束。迁移失败后必须能够回滚并在下一次启动重试。

## 5. 下载中心任务状态机

### 5.1 创建前

1. 优先检查最近一小时内同店、同维度、同日期且已校验的本地文件；
2. 检查当前区间的 manifest；
3. 没有 manifest 才进入下载中心获取 baseline；
4. 首帧空表视为“页面可能仍在加载”；
5. 只有连续稳定快照，或连续出现页面明确的“暂无数据/暂无记录”空态，才认为 baseline 就绪。

### 5.2 提交时

在所有维度、日期、单选项和弹窗门禁通过后，紧邻“确定”点击执行：

1. 再次读取页头，精确核验注册表 `shopName + shopId`；
2. 用当前时间生成 `createdAt`，并把 `storeKey + shopName + shopId + dimension + 日期范围` 写入 manifest；
3. 原子写入 `status=submitting` 的 manifest；
4. 写盘成功后才点击“确定”。

如果写盘失败，必须停止，不能创建无法追踪的远端任务。

### 5.3 重启恢复

下载中心的任务标题不包含 SKU/SPU 维度，因此不得按“最新任务”或同名第一行恢复。只接管：

- 不在 baseline 中；
- 标题完整匹配；
- 创建时间与 manifest.createdAt 邻近；
- 能唯一对应的任务。

找不到或出现多行歧义时保留 manifest 并停止，禁止再建一条任务。

如果现场证据确认旧 manifest 是在错误店铺身份下创建（例如 manifest 期望 `701455`，同一确认时间只出现 `711743` 任务），不得把错误店任务补写为该 manifest 的指纹，也不得删除京东侧任务。应将 manifest 原样原子改名为带 `identity-mismatch` 与时间戳的审计归档；修正当前 profile 的店铺登录后，才允许从新 baseline 建立正确任务。

店铺 SKU 主数据的 `active-task-<storeKey>.json` 若仅保存 baseline、从未观察到 `taskId`，也不能无限期阻塞后续新增 SKU。只有同时满足以下条件才可放弃：`createdAt` 有效且至少过去 30 分钟；当前导出记录已经两次相同的非空快照，或两次明确“暂无数据/暂无记录”空态；按确认时间窗口匹配到的新任务数为 0。已知 `taskId`、时间未到、快照未确认、一个候选或多个候选都必须保留清单并失败关闭。空态只可由同一、唯一“刷新列表”控件所处的导出容器确认，页面其他区域的空态不能作为证据。放弃前必须原子 rename 为同店、带时间戳的审计归档，并记录 `recovery_abandoned`、归档文件名和原恢复清单的 `createdAt`；审计写入失败时不得继续点击新建任务。不得删除证据；随后才可建立新的 baseline。

京麦“菜单更新调整”遮罩仅在唯一可见弹层同时命中“京麦菜单更新调整”或“一级菜单更新调整”与生效说明，且其中唯一按钮精确为“知道了”时才允许点击并等待隐藏。“立即查看”“去处理”“确认”等任何其他按钮均不点击。

WareList 的店铺 SKU 任务行下载由 `window.open(jobExecFileRst, '_blank')` 触发，不能只等待当前页面的 Playwright `download` 事件，也不能重放可能一次性的签名 URL。下载前必须先在 Chrome 根 CDP 会话设置 `Browser.setDownloadBehavior=allowAndName` 到当前店铺下载目录内的受控临时目录，并监听唯一的 `Browser.downloadWillBegin/downloadProgress` GUID。开始事件的 URL 必须是 HTTPS、`storage.360buyimg.com`、`/ware-common/cpop-export-sku/`、`.xlsx`、精确任务 ID 及 `Expires/AccessKey/Signature` 三个签名参数；建议文件名也必须为 `.xlsx`。取消、超时、多个开始事件、错误 GUID、暂存路径越界、空文件、非 ZIP/XLSX、缺少 `商品编码` 或 `SKUID`、业务行数与任务“成功”行数不一致时均失败关闭。只在完成后验证暂存文件并原子 rename 为当前店铺目录内的规范文件；不得扫描历史文件、不得使用其他店铺目录、不得再次点击下载。

## 6. 工作簿验证

商智工作簿必须按表头而不是文件名识别维度：

- SKU：必须且只能命中 SKU 标识列；
- SPU：必须且只能命中 SPU 标识列；
- 同时含 SKU 和 SPU 标识，或标识为空，均拒绝。

日期验证应生成 `[startDate, endDate]` 的完整自然日集合，并比较实际业务日期：

- 缺任何一天：拒绝；
- 存在区间外日期：拒绝；
- 汇总行：只按明确汇总语义跳过，不能误删正常商品行。

## 7. 对抗审查流程

### 阶段一：出题

按以下视角检查：

- invalidation：枚举所有能修改底层数据或恢复状态的写路径；
- race：检查 baseline、点击、manifest 写入、下载落盘和批次写入的交错；
- boundary：检查空表、单日、跨月、每月 1 日、缺中间日期、多个同名任务；
- authentication boundary：检查空白业务 URL、延迟 passport 重定向、pending 超时、唯一登录表单、单次提交、验证码/安全验证、凭据拒绝和登录后店铺身份；
- transaction：检查下载成功但导入失败、数据库迁移中断、写盘失败后是否误点击；
- contract：对照注释、文档、HTTP 状态、哨兵 schema 和实际行为。

每个主张必须提供文件行号、可达操作序列、预期、实际和影响范围。

### 阶段二：独立证伪

验证者必须重新逐行读最终源码，主动寻找主张不成立的原因，包括：

- 是否有其他门禁覆盖；
- 路径是否真实可达；
- 时间、字段和状态码前提是否成立；
- 修复是否只改了测试 helper，生产调用点仍旧错误；
- 旧数据库迁移是否保留数据、替换约束并支持失败重试。

验证者不得直接信任实现者的测试数量或结论。

### 阶段三：终审

主代理只在独立复审 PASS 后交付，并单独执行：

```powershell
node --import tsx --test tests/*.test.ts
node --test tests/rendered-html.test.mjs
npm run build
git diff --check
```

安全 dry-run：

```powershell
npm run jd:all-stores -- --dry-run --store-key <store-key> --mode all
```

正确结果应为所选店铺 3 个 `planned`、0 个 `completed`，且不启动浏览器、不创建京东任务、不调用导入 API。

## 8. 真实上线冒烟

离线终审通过后仍不应直接四店全跑。获得明确授权后：

1. 选择一个已登录店铺；
2. 使用明确日期范围，先执行单店；
3. 核对下载文件、审计 JSON、批次店铺和日期覆盖；
4. 确认没有重复任务、串店或错误批次；
5. 再按注册表顺序扩展到其余店铺。

单店失败后使用 `--store-key <注册表键>` 重跑该店，不重跑全部四店。

## 9. 速度优化边界

允许的提速方式：

- 复用最近窗口内且通过完整验证的本地文件；
- 对明确登录失效快速失败；
- 单店失败后只重跑失败店铺；
- 明确空态连续确认后快速完成 baseline；
- 审查和离线测试并行执行互不修改文件的工作。

禁止以牺牲正确性提速：不得跳过日期全集校验、不得按最新任务猜测、不得并行共享浏览器状态、不得把下载当导入完成。

## 11. n8n 三段式工作流

`automation/n8n/jd-multi-store-daily.workflow.json` 默认保持 `active=false`，仅以环回 HTTP 编排：

```text
A POST /jd/plan → B POST /jd/run → C POST /jd/verify
```

定时和手动入口在 A 前统一调用 `POST /coordination/claim`，以 `workflow key=jd + n8n execution ID` 原子领取一次性 helper；未获授权时每 5 分钟等待，累计 72 次、约 6 小时后以 `coordination_wait_expired` 失败关闭。等待阶段尚未启动浏览器、创建京东任务或调用导入接口；原 owner 失败并退出 helper 后，等待 execution 才能重新领取并从 A 开始。禁止用先查 `/health` 再调用 A 的非原子检查代替领取。

- 调度为 `10:00`（`Asia/Shanghai`）。A 固化“昨天所在月 1 日至昨天”的扫描范围，逐店、逐 SKU/SPU 维度读取权威覆盖，验证响应未截断且实际日期/缺失日期完整互斥，再把相邻缺失日合并为连续下载区间；每月 1 日扫描上月完整范围。
- B 按店铺严格串行：商品主数据每天固定更新一次；SKU/SPU 只执行 A 生成的缺口区间，无缺口维度不创建任务。失败会持久化同一 `runId`、分步计划与 runner 审计；恢复只跳过已完成且可复核的精确步骤，从首个失败/未完成步骤继续，绝不重新创建已完成店铺主数据或日数据导出任务。
- 持久计划绑定 n8n execution ID：同一 execution 在响应丢失后可以复用已执行/已完成计划继续 C 阶段；新的 execution 遇到 completed 计划必须创建新的 `runId` 并重新导出，以便新增 SKU 可见。新的 execution 只能接管同身份的 planned、failed 或 executed 计划；running 计划一律拒绝接管。
- A/B 会重新核对有序店铺身份（`storeKey + shopId + shopName`）；注册表变更拒绝旧计划。
- C 同时复读每个受控 runner 审计和本机 `/api/netshop/import?batchId=...` 的精确批次，核对 `completed`、source、dataset、platform、shop、零告警、行数和该缺口区间；全部批次通过后，再回查四店 SKU/SPU 的整个扫描范围必须无剩余缺口。
- 三段必须使用同一 `X-TERUISI-N8N-EXECUTION-ID`。空 ID、跨执行接管、并发、乱序均失败关闭。helper 不返回账号、密码、Cookie、Token、Session 或 profile 路径；运营系统仅在 `operator/admin` 且 helper 就绪时展示编辑器。
