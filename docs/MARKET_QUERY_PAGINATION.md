## 问题和用户行为

原 `overview(view=ranking)` 在返回一页 20 条之前，先读取筛选范围全部榜单、价格快照和关联销售；超过 250,000 条原始记录时返回 413。首次失败还会提前返回错误页，隐藏市场子菜单和筛选栏。

当前版本始终显示子菜单、搜索、独立筛选选项及日期编辑器。失败可以调整条件、重载或切换设置；不同日期、筛选和视图的旧数据不在新条件下显示。同条件刷新失败保留上次结果并明确提示。网络恢复触发一次只读刷新，GET 的 30 秒期限包含响应体读取，不重放写入。

榜单改为上一页／下一页，每页 20 条，替换当前页而不持续追加 DOM 和记录；已选竞品跨页保留。页面显示读取时间。日期编辑应用到现有全局统计周期。

## 查询契约

- 新 `backend/market/ranking_query.py` 使用 ORM 编译的既有筛选条件和参数化 SQL，在数据库完成价格段来源去重、计数、价格带选择、排名排序、上一期排名及上榜期数，再 LIMIT/OFFSET 返回当前页 ID。
- 去重保持完整周期、类目、scope、SKU/SPU 和编码；“全部”来源优先，其次空来源，再按原价格段文本和最新 ID。商品数量按独立身份列分组，不拼接字符串。
- 正式价格仍要求 confirmed、三种正式价类型、合法 64 位图片哈希及正数确认价。价格带仍按已发布类目优先、通用兜底、有效日期、左闭右开金额区间处理。候选价不参与正式价格带。
- 网店 projection 必须绑定 active revision、`jd_sku_daily` 来源、SKU/SPU 数据集和精确闭区间周期；仅正合计替换榜单 GMV，并在排序前生效。关联销售只为当前页调用，继续核验销售 revision 和完整编码回包。
- 筛选选项和图片状态使用数据库 GROUP BY，不把每条原始记录传入 Python 计数。`GET /api/market/filters` 独立于榜单和行业汇报，沿用角色、无限制数据范围、HMAC、reader 与市场 revision 检查。
- 请求页码上限为 1,000,000，公开解析与后端一致；单页仍限 10–50。深页仍可能耗时，受既有服务和数据库期限控制。

## 本次范围和限制

此变更解除了**商品榜单分页**对 25 万条原始记录和 2 万个全范围关联销售商品的依赖，没有放大行业汇报的计算额度。行业汇报的复杂趋势、机会矩阵等仍使用原有界计算路径；超过原上限需缩小范围，期间其他市场子页面继续可操作。不能称为行业汇报已全部迁成 SQL 聚合。

无数据库迁移、新角色或新写权限。本次按用户授权受控启停生产服务；未人工执行模型、导入生产数据或发送业务通知。既有“主数据与价格”列表超时、workerd 内存增长及长期运行自动恢复不属于已解决的结论。

## 正式数据复验补充

首轮上线验证暴露生产数据形状下的 6 秒 SQL 超时，不能用空价格快照的 25 万条合成测试代替这一验收。补充优化使用 PostgreSQL DISTINCT ON 保持原来源优先级并改善去重行数估计；价格带按不同类目、周期末日与正式价格计算一次；网店投影采用可等值关联的身份表达式，并固定只聚合一次。无价格带筛选时，计数不计算价格带，取页不加载全范围价格；当前页正式价格仍由原有精确快照函数解析。先确定当前页身份，再计算这些身份在完整筛选范围的前期排名和上榜次数。

2026-09-15 补充源码在正式市场 reader 的只读会话验证全范围三条 SQL 为 4.557、3.915、3.811 秒，保留 6 秒上限；未修改生产角色或数据库配置。中间版本隔离 PostgreSQL 65 项和 reader/writer 正负权限检查通过，后续增加以下回归用例。

补测冷缓存与“未确认价格”时，先读取响应原本需要的独立筛选聚合；未确认价格行直接分流，避免把空价格行带入价格带关联排序，计数中间结果只保存所需标量。实际六组筛选合计 5.970 秒，随后三条 SQL 为 4.033、3.397、4.407 秒；单条 SQL 仍限 6 秒。增加无匹配价格带的合法确认价与 250,002 条未确认价格筛选回归，最终隔离 PostgreSQL 66 项及真实角色正负探针全部通过。
