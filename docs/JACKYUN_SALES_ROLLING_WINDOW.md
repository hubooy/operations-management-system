## 业务口径

销售单明细账沿用发货时间及既有下单时间缺失回退口径，每次完整同步截至上海业务日期的昨天，包含昨天在内共 45 个自然日。结束日为运行日减 1 天，开始日为结束日减 44 天。2026-09-23 执行时为 **2026-08-09 00:00:00 至 2026-09-22 23:59:59**；2026-09-01 执行时为 7 月 18 日至 8 月 31 日。跨月、跨年、闰日和月初均按同一规则，不再按月截断。

每次成功采集、完整校验并发布的新快照更新该范围的明细：金额、数量等变化采用本次新值，窗口内本次不再出现的旧明细按原完整范围替换规则移除；其他日期与渠道的历史保留。同范围同内容沿用原幂等规则，不把多次导入的数量和金额累加。新同步仍按原全局 helper/吉客云锁串行，未决导出或未闭合运行不得跳过。

“最新”在这里指本自动链路本次新获取且成功验证发布的完整快照，不以文件名或文件修改时间排序。本改动不增加任意历史手工文件、不同执行器迟到文件的来源水位协议，也不改变发货时间为取数范围的口径。

货品、分仓库存、库龄与组合装四表的日期/范围保持原规则。销售库存成本匹配、零成本清洗、仓库过滤、渠道白名单、来源行数校验及五表全部校验后才导入的门禁保持原规则。

## 日期如何贯通

新 `plan-api` 创建 v2 计划，显式保存 `salesStartDate` 和原 `asOfDate`；同一 execution 重试不重算日期。v2 缺少起始日、不是完整 45 天或运输协议不匹配均拒绝。历史 v1 计划仍保留原月度含义，不能把旧月度文件解释为 45 天数据。

共同的 `lib/jackyun/sales-period.ts` 用于计划、商家 API 查询/导出条件、交接日期读回、销售预处理、元数据与分片上传范围、导入演练和独立批次回查。控制器保存并比对起始日；输入摘要为携带起始日的销售合同使用 v4，未携带该字段的旧合同仍按原 v3 字节算法核验。处理子流程返回的日期范围也必须与父运行一致，原始和处理后文件仍核对完整摘要。

API 任务续跑保留原起始日并比较控制状态，月度控制器不能接管滚动计划。既有页面异常的零业务关闭 operator 支持 v2，仍执行原身份、日期、摘要、helper 空闲和业务效果不存在门禁；不会自动关闭任何失败运行。

## 订单更新与滚动边界

复用 Django/PostgreSQL 原有全销售写入基域锁、输入归属、状态 token、内容指纹、事务内 upsert 和范围内旧行清理，没有新增业务表或迁移。

补齐一个已在隔离库复现的边界：当窗口移动但明细恰好不变时，旧代码会把它当成缺少元数据的历史兼容数据，返回旧范围及旧文件回执。现在已具备完整范围元数据的现代批次走正常新范围发布，事实行不重复，归属与新范围/新原文件一致。同范围同内容仍返回 duplicate；真正缺少范围元数据的历史兼容去重保留。
