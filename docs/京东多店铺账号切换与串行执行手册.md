# 京东多店铺账号切换与串行执行手册

## 目的

本手册用于店铺 SKU、商智 SPU 分天和商智 SKU 分天任务的多店铺运行。系统通过店铺注册表和独立 Chromium profile 隔离账号，按顺序完成一个店铺后再切换下一个店铺。

## 安全边界

账号密码不得进入 n8n、注册表、环境变量、命令参数、Markdown、Skill、日志或 Git。需要自动登录的受控店铺只允许使用 `loginMode=windows_dpapi_credentials`：操作员在 PowerShell 中交互录入，凭据仅以当前 Windows 用户绑定的 DPAPI 密文保存到 Git 已忽略的 `.runtime/jd-credentials/`。程序只在内存中解密，不回读输入框内容，提交后立即清空内存字段。

Cookie 和登录态只由对应 Chromium profile 自身持久化，不得导出到配置、工作流、审计或文档。验证码、短信、滑块、安全验证和账号异常不得自动绕过；出现这些情况时必须失败关闭并由操作员处理。

## 店铺注册表

文件：`config/jd-store-accounts.json`

每项至少包含：

- `storeKey`：脚本使用的稳定键
- `accountLabel`：账号提示标签，不是密码
- `shopName`、`shopId`：店铺识别信息
- `browser.executablePath`：受控 Chromium 程序
- `browser.userDataDir`：Chromium 用户数据根目录
- `browser.profileName`：`Default` 或 `Profile N`
- `browser.profileDir`：`userDataDir/profileName` 对应的实际独立 profile 目录
- `browser.debugPort`：独立 CDP 端口
- `browser.downloadDir`：独立下载目录

当前四店映射为：

| 店铺 | `storeKey` | Chromium Profile |
|---|---|---|
| 志高商用设备旗舰店 | `jd-yiyong-director` | `Default` |
| 志高商用厨电旗舰店 | `jd-chudian-weizhang` | `Profile 1` |
| 志高切肉机旗舰店 | `jd-maidehao-operator1` | `Profile 2` |
| 志高商用洗碗机旗舰店 | `jd-cuizhiwang-dengweizhang` | `Profile 3` |

四店可以共享同一个 Chromium 安装和 `userDataDir`，但实际使用四个固定、互相隔离的 Profile；流程不会在同一个浏览器页面内切换店铺。修改注册表后，必须检查店铺键、shopId、端口、解析后的 `profileDir` 和 `downloadDir` 均不重复，`profileDir` 必须精确等于 `userDataDir/profileName`，并确认目录可用；平台字段只能是 `京东`。

## 凭据配置与登录守护

在项目目录中为每个店铺分别执行一次；修改密码后执行同一命令即可覆盖该店旧密文：

```powershell
Set-Location -LiteralPath "D:\运营管理系统"
npm run jd:credential:setup -- -StoreKey jd-yiyong-director
npm run jd:credential:setup -- -StoreKey jd-chudian-weizhang
npm run jd:credential:setup -- -StoreKey jd-maidehao-operator1
npm run jd:credential:setup -- -StoreKey jd-cuizhiwang-dengweizhang
```

每条命令只在 PowerShell 中交互询问当前店铺的账号和密码。密码输入不会回显；完成时只应返回 `status=stored` 和对应 `storeKey`，不得把账号或密码复制到聊天中。

只检查某店是否已配置密文而不读取凭据：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/jd-credential-vault.ps1 -Action status -StoreKey <店铺键>
```

登录守护固定按以下顺序判断：

1. 启动注册表指定的 Chromium Profile，先复用已持久化的登录会话；
2. 对初始空白页、加载中页面和可能延迟发生的京东登录重定向做有界等待；只有识别到受控业务页面才能认定已登录；
3. 确认进入唯一账号密码表单、页面没有验证码或安全验证且店铺启用 DPAPI 模式后，读取该店密文，在内存中填入并最多提交一次；
4. 提交后必须再次识别受控业务页面，并继续精确核验页面 `shopName + shopId`；仅 URL 离开登录页不算成功；
5. 登录状态一直无法确认、凭据缺失/损坏/被拒绝、表单歧义、验证码、安全验证或身份不符时失败关闭，不得换用另一店凭据或重复提交。

首次登录或平台要求人工验证时，只处理程序指出的当前店铺 Profile。普通恢复模式可以打开该店可见 Chromium；操作员完成验证并确认店铺身份后关闭窗口，再从原失败步骤安全续接。`--interactive-login` 是显式人工维护模式，不能与 `--no-visible-recovery` 同时使用；它属于业务脚本参数，可能在登录完成后继续当前步骤，不能当作无副作用的纯登录查看器。

四店共享同一 Chromium 用户数据根目录，因此只能由受控 runner 严格串行启动；如果普通 Chromium 窗口正在占用该根目录，自动任务必须失败关闭，不得强制结束未知窗口。

## 运行方式

单店店铺 SKU：

```powershell
npm run jackyun:ware-export -- --store-key jd-yiyong-director
```

单店商智 SKU：

```powershell
npm run jdsz:product-detail-export -- --store-key jd-chudian-weizhang --dimension SKU --start-date 2026-07-01 --end-date 2026-07-19
```

全部店铺串行运行（`--mode all` 固定按主数据、SKU 日数据、SPU 日数据执行）：

```powershell
npm run jd:all-stores -- --mode all --start-date 2026-07-01 --end-date 2026-07-19
```

只跑一种日数据时使用 `--mode sku-daily` 或 `--mode spu-daily`；只重跑失败店铺时加 `--store-key <注册表键>`。`--dry-run` 只写入 `planned` 审计，不会标记完成。执行器一次只启动一个店铺，成功后才切换下一个店铺；任何失败都会停止，不会自动跳过。

完全静默运行时增加 `--no-visible-recovery`。该模式仍使用后台有头 Chromium 并直接保存下载文件，但登录、验证码、安全验证或店铺身份异常时只失败关闭并保留审计，不打开可见窗口；需要人工登录时另行显式使用 `--interactive-login`，两种模式不得同时混用。

每轮只写一个 `outputs/jd-multi-store-runner/run-*.json` 审计文件。步骤会依次记录 `planned/running/completed/failed`，失败项包含子进程 stderr 摘要；成功项记录下载路径、批次 ID 和行数。不要把下载完成当成已导入，只有子程序 JSON 中带有通过验证的批次结果才表示已自动导入。

## 故障恢复

1. 记录失败的 `storeKey`、阶段、任务 ID、审计文件和下载目录。
2. 若错误为登录状态未确认，先允许京东完成延迟重定向；不得因当前 URL 看似为业务地址就直接判定已登录。
3. 检查对应 Profile 是否仍登录、页面 `shopName + shopId` 是否匹配、凭据状态是否就绪，以及是否存在多个待处理任务。
4. 验证码、短信、滑块、安全验证或凭据被拒绝时只人工处理当前店铺；不得重复提交登录、换用另一店 Profile 或绕过平台验证。
5. 不要重复点击未知任务，也不要盲目复用“最新”任务。
6. 修复后只重跑失败店铺，例如 `npm run jd:all-stores -- --store-key jd-chudian-weizhang --mode all`，验证导入结果后再继续后续店铺。

## 常见检查

```powershell
rg -n --hidden --glob '!node_modules/**' 'password|secret|token|Cookie' config .agents/skills docs
git diff --check
```

检查结果不得包含实际密码或会话凭据。
