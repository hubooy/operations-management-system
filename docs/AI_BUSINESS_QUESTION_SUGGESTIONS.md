# 经营分析问题范围候选（整合候选）

`lib/ai/business-question-suggestions.ts` 提供纯函数 `suggestBusinessQuestionScope`，把中文问题中少量明确的日期和数据目的转换成工作台待确认候选。它没有网络、数据库、模型或任务写入；返回值固定为 `authorityVerified=false`、`requiresUserConfirmation=true`。后续 UI 必须让用户核对具体范围，再调用原有来源目录选择和服务端预览。目录标量由调用者从已验证的 owning 目录页提供，纯函数不会自行证明目录版本或账号权限。

输入包含问题、显式 `shanghaiToday`、当前表单范围，以及精确来源标量。不得用 `Date.now()` 或模型自己的时钟推导业务日期。问题最长 1000 Unicode 码点和 4000 UTF-8 字节；目录至多 1000 个标量、规范序列化后最多 128 KiB。函数不会修改输入。

仅识别以下表达：

| 表达 | 候选处理 |
| --- | --- |
| `近30天` | 截止上海时间昨天、包含此前共 30 个完整自然日；今天不作已导入日期。若同时写了“今天/今日”，保留截至昨天候选并明确提示冲突，须人工确认。 |
| 唯一的 `YYYY-MM-DD至YYYY-MM-DD` 等明确区间 | 以明确日期为准；必须在 2000—2098 年、截止昨天、连续 1—93 天。与 `近30天` 同时出现时提示冲突。 |
| `同比`、`环比` | 在现有表单窗口上增加 `yearAgo`、`previous`；始终包含 `current`。 |
| 推广/投放/广告/关键词/搜索词、SKU、SPU、B端/B2B/企业购/批发、市场/行业/竞品/榜单 | 分别产生 `promotion`、`sku`、`spu`、`b2b`、`market` 数据目的；无相应精确来源时列出缺口。 |

店铺仅从已验证目录中匹配当前表单的完整平台及店铺身份，或匹配问题明确写出的 `店铺：完整名称` / `网店：完整名称`。同名跨平台保留所有候选并提示人工选择。市场条件只沿用表单完整五字段身份，或从 `类目：完整名称` 匹配目录候选；同名多榜单条件不猜。普通叙述中出现局部名称、别名或近似名字不会获得精确来源身份。模糊或缺少来源时保留缺口，绝不补造店铺、类目、渠道或数据集。

候选包含两个环比日期视图：`previousEqualLength` 是现有经营分析的前一等长区间；`previousMonthSameDates` 仅在本期属于同一自然月时展示销售概览可能采用的上月同期。两者只供核对，不修改旧报告的固定版本或服务端比较规则。最终日期、来源、覆盖和容量仍以服务端预览及采集后证据为准。

工作台现在提供“从问题生成范围建议”。点击时用 `business-time` 中显式的 `Asia/Shanghai` 日期生成候选，并显示所用业务日期。页面只把当前账号下三个既有来源选择器成功 `onSelect` 的精确标量保存在内存中；账号变化即清空，手工删除或修改来源时按当前表单逐项剔除，手填相同文字不能恢复目录证明。候选只在用户点击“应用日期与比较窗口”后写入这三个表单字段；不会添加店铺、ERP 渠道、市场条件或创建任务。任何表单编辑都会使旧候选、来源预览和采集确认失效。现有服务端预览、账号复验与未知提交原样重试逻辑继续负责最终提交。

隔离浏览器 `tools/business-question-workbench-ui-rehearsal.mjs` 覆盖手填身份不冒充目录、人工应用、明确日期与近30天冲突、来源手改失效、账号切换及迟到目录结果、原请求未知结果重试、390px 页面无水平溢出。该演练只连合成 loopback API，不触发正式采集或模型。
