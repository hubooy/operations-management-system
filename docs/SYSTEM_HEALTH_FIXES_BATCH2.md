## H01：主数据与价格全量整理后分页（P1，已修复并验证）

- **现象与触发：** 打开主数据默认列表，原实现先遍历所有匹配行，为每行查询价格、图片、品牌、累计成交额、标注和价格带，再返回一页。匹配量增长会线性增加 SQL、Python 对象和内存；历史正式环境出现约 30 秒超时。
- **影响范围：** 主数据列表及待确认价格列表；历史模式按月份选择代表行。
- **原因：** 分页在 Python 全量整理之后，存在逐行关联查询。
- **修复：** `master_query.py` 在数据库完成既有字段筛选、代表行选择、价格/来源/标注状态筛选、累计 GMV 排序、计数和页码校正；仅加载当前页对象并批量读取关联信息，价格带规则只读取一次。全部请求参数继续绑定，不拼接用户输入。
- **保持的口径：** 基础筛选先于代表行选择，状态筛选在代表行选择之后；保留最新身份、历史月份、完整类目/scope/SKU-SPU 身份、图片哈希、价格候选优先级、同分排序和越界页码回退。主数据原有零/负确认价判断与榜单的正数规则分别保留。并发删除页内行时返回可重试的只读 503，不返回残页。
- **验收：** 与冻结的旧分页算法逐字段比较默认、历史、空结果、搜索、价格来源、确认状态、标注状态、多个筛选交集及越界页码；校验当前页富化次数和 SQL 数量不随总条数增长。5 万身份的默认、翻页、筛选及并发实测见下表和证据。

## H02：榜单重复聚合与排序（P1，已优化并验证）

- **现象与触发：** 无日期限制地读取全范围榜单。历史正式读取约 12–13 秒；本轮隔离数据也复现明显卡顿。
- **证据与原因：** 分阶段采样显示主要时间位于 `ranking_page`，原统计、价格带计数、分页三条 SQL 重复进行去重和价格关联；另有六次全表筛选项统计，以及全范围网店成交额投影。
- **修复：** 三条 SQL 合为一次，复用请求内中间结果；全局筛选项改为一次 `GROUPING SETS` 扫描。只让符合原正式价格规则的快照参与价格关联，并减少中间结果携带的列。64 位十六进制哈希在 PostgreSQL 使用等价的长度及字符集合检查。
- **排序和历史：** 榜单先按名次排序，因此先保留目标页之前及页边界所有同名次记录，再计算关联成交额进行精确排序；不能按原始 GMV 提前截断。选定页后，单独计算这些完整身份的历史排名和上榜次数，包含不在当前候选名次内的历史记录。
- **一致性与边界：** 继续复用市场版本前后核验、销售 revision 和完整销售回包校验；销售仅查询当前页。没有新增跨请求缓存，没有放宽 6 秒 SQL 期限、请求期限或行业汇报的数据上限。
- **验收：** 与原完整报表路径及旧榜单实现比较整份响应，覆盖多月、同名次跨页、空名次、跨 scope/SKU-SPU、来源去重、投影先于排序、无匹配价格带、无效哈希、价格边界和空结果。

## 最终性能结果

隔离库包含 **32 万条原始榜单（去重后 30 万条）、5 万商品身份、30 万价格快照、15 万网店投影、10 万真实结构的销售行、5 万图片缓存和 2.5 万标注**，跨 6 个月、7 类目、13 品牌。全部为合成数据。

| 页面 | 单用户 P50 / P95 | 四用户 P50 / P95 | 样本及错误 |
|---|---:|---:|---|
| 主数据默认列表 | 0.34 / 0.39 秒 | 0.48 / 0.56 秒 | 各 20 次，0 错误 |
| 榜单全范围 | 4.58 / 4.68 秒 | 5.13 / 5.27 秒 | 各 20 次，0 错误 |

同库、同索引的新旧整份响应比较通过。榜单第一页从 **12.17 秒降至 4.55 秒**，减少约 63%；第二页、未确认价格和单月范围也逐字段一致。主数据同样 1,000 身份从 4.49 秒降至 0.14 秒，核心 SQL 从 **7,001 条降至 10 条**；签名 API 的 5 万身份默认页为 12 条 SQL，包含两次市场版本核验。

首次进程请求分别为主数据 0.83 秒、榜单 4.52 秒；不是清空操作系统及数据库缓存后的冷启动。翻页、空结果、典型筛选和历史模式各记录首次/重复读取，见完整样本。

**榜单 3 秒 P95 的建议目标尚未达到。** 本轮确认了约 63% 的同库提速及原期限内的四用户稳定性，不能表述为“全部性能目标达标”。正式环境的速度仍需上线后低频只读验收。

单用户中位阶段耗时：主数据数据库选页约 296 毫秒、当前页批量富化约 32 毫秒；榜单筛选项约 216 毫秒、数据库榜单聚合及分页约 4,156 毫秒、当前页真实销售读取约 9 毫秒、JSON 序列化约 0.27 毫秒。SQL 仍是榜单主要剩余成本。四用户最大单条 SQL 约 4.81 秒，未放宽 6 秒限制。

Python 分配峰值单独开启 tracemalloc 测量，耗时不混入普通性能样本：同 1,000 身份主数据旧版约 2.92 MiB、新版约 0.38 MiB；5 万身份新接口约 0.35 MiB，32 万榜单新接口约 0.22 MiB。这不是进程 RSS、数据库内存或长期内存增长结论。
