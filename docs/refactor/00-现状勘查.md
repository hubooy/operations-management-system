# TERUISI 运营管理系统前端重构：阶段一现状勘查

> 勘查日期：2026-08-17（Asia/Shanghai）
>
> 范围：只读检查当前仓库前端、相关 API 契约、测试与本机运行页面；本阶段未安装依赖、未修改业务代码、未部署。
>
> 参考：[Ant Design Menu 导航菜单](https://ant.design/components/menu-cn) 与用户提供的 `前端重构提示词.md`。

## 1. 结论先行

当前仓库与参考提示词描述的项目不是同一套技术底座，不能直接执行其中的“React 18 + antd 5 + ProComponents + DRF”迁移步骤。当前系统实际是一个 Next.js 16 / React 19 / Vinext / Cloudflare Workers / D1 / R2 应用，前端尚未依赖 Ant Design，业务页面主要集中在一个 5,978 行、约 471 KB 的 `app/page.tsx`，全局样式集中在一个 1,752 行、约 265 KB 的 `app/globals.css`。

最值得优先处理的不是“立即把所有表格换成 ProTable”，而是先拆出稳定的应用外壳、导航模型、请求客户端、页面路由状态和设计令牌。否则直接引入 ProComponents 会把现有的状态、权限、请求和 35 张手写表格继续包在一个超大客户端组件中，依赖增加了，但结构性问题仍然存在。

Ant Design 菜单页最适合当前系统借鉴的是以下交互范式：

- 左侧导航按业务域分组，选中项唯一、层级清晰；
- 内嵌菜单可折叠，折叠后保留图标与 Tooltip；
- `selectedKeys`、`openKeys`、折叠状态由应用控制，刷新与深链可以还原；
- 浅色/深色主题与组件状态由统一 Design Token 驱动；
- 使用真实 `menu/menuitem` 语义、键盘操作与清晰焦点态；
- 在 Flex 布局中给菜单容器正确设置收缩边界，避免菜单无法响应式省略。

## 5. 手写壳与表格盘点

静态统计：

- `app/page.tsx`：21 张 `<table>`、84 个 `<input>`、3 个 `<form>`；
- `app/market-view.tsx`：14 张 `<table>`、17 个 `<input>`、13 个 `<select>`；
- `app/market-annotation-view.tsx`：2 张 `<table>`、18 个 `<input>`、8 个 `<select>`；
- 目前共至少 37 张显式原生表格，其中 35 张位于主要业务页面文件；
- `TableColumnFilters` 通过 DOM 扫描为所有已渲染表格追加列筛选，是当前的全站兼容能力。

### 适合优先抽取的公共壳

1. `AppShell`：品牌区、分组导航、折叠/移动端抽屉、用户区；
2. `GlobalHeader`：模块标题、数据周期、全局搜索、通知；
3. `ModuleTabs`：受控 tab、URL 同步、键盘与 ARIA 契约；
4. `DataState`：loading/error/empty/permission 四态，禁止把请求失败渲染成“暂无数据”；
5. `DataTableShell`：工具栏、服务端分页、列设置、筛选摘要、横向滚动；
6. `FormField` / `Dialog` / `Drawer`：统一错误聚焦、关闭与焦点恢复；
7. `apiClient`：鉴权错误、JSON 解析、AbortSignal、错误对象与 `no-store` 统一处理。

### ProTable 与逐页迁移判断

当前没有可“一次替换、全站收益”的 `RuleTable`。现有 `TableColumnFilters` 是运行时 DOM 增强，并不拥有列定义、分页或请求。因此不能只把它的底层换成 ProTable。

如果后续确认引入 Ant Design，建议先做 1 个低风险、服务端分页的列表试点，再决定是否采用 ProTable：

- 适合试点：导入历史、工作计划列表、网店货品目录；
- 暂缓：市场 AI 复核、库存备货、AI 模型/渠道设置、大文件导入；
- 迁移期间保留 `TableColumnFilters`，只对已迁移表格显式退出 DOM 增强，避免双重筛选。

## 6. API 与请求层实测

### 6.1 当前事实

- 页面代码中约有 89 处直接 `fetch()`；没有统一 `api.js` 或 typed client；
- 大部分读取显式使用 `cache: "no-store"`，部分请求带 `AbortController`，但写法分散；
- 列表参数通常使用 `page` / `pageSize`，筛选多值通过重复 query 参数传递；
- 50 个 API Route Handler 的成功响应由各领域定义，并非统一 DRF 结构；
- 常见成功形状包括 `{ items, pagination }`、`{ items }`、领域 workspace、`{ ok, item/result }`；
- 常见失败形状是 `{ error, code? }`，鉴权统一可返回 401 `authentication_required` 或 403；
- `app/api/auth/me` 成功为 `{ user }`，失败走统一授权响应。

### 6.2 当前边界问题

1. `Home` 读取 `/api/auth/me` 时对非 2xx 和网络错误静默忽略，随后把用户显示为“访客 · 只读查看者”；这不是完整登录墙，也会让鉴权失败和匿名只读看起来相同。
2. 请求错误提取、JSON 解析、401 跳转、403 提示、AbortError 忽略在各页面重复实现，语义不完全一致。
3. 不同列表的 `pagination` 形状虽大体接近，但没有统一类型与适配器；不能直接建立 DRF 专用 ProTable 转换器。
4. 有些复合视图并行调用多个 API，直接交给 ProTable `request` 会丢失跨卡片协调、取消旧请求和局部错误展示能力。

### 6.3 后续应建立的请求契约

先为当前 Route Handlers 定义统一的 `ApiError`、分页查询、排序和重复筛选参数，再按页面需要适配 Ant Table/ProTable。适配器必须保留：

- `AbortSignal` 与迟到响应门禁；
- 401 登录、403 无权限、4xx 参数错误和 5xx 服务错误的不同反馈；
- `success: false` 只作为组件协议，原始错误仍要可见；
- 多值筛选继续使用重复参数，不能静默改成逗号拼接；
- 金额仍以人民币分传输，展示层才格式化为元。

## 8. 布局、主题、取数与权限冲突面

### 8.1 布局与 URL

当前模块、页内 tab、筛选与统计周期都主要存在 React state。布局重构应先确定 URL 契约，例如 `/?module=sales&view=channel` 或真实分段路由；在此之前直接替换 Menu 只能改变外观，不能解决深链和刷新还原。

当前 sticky 顶栏固定在 `top: 0`，部分市场区域还有自己的 sticky 元素。后续若引入 ProLayout，需要定义唯一的 header 高度 CSS 变量/Context，禁止在各模块新增字面偏移。

### 8.2 主题与 Design Token

`globals.css` 根部已有颜色、阴影和侧栏宽度变量，但大量规则仍直接写十六进制、rgba、字号和圆角。当前没有 ThemeProvider、深色内容主题或首帧主题脚本。应先建立语义令牌（背景、表面、文字、边框、品牌、上涨、下跌、警告、焦点、层级、间距、字号），再把这些令牌映射给 Ant Design；不能反过来让 Ant 默认 token 成为新的业务事实源。

业务口径要求涨红跌绿。当前已有多处 green/red/orange 状态色，迁移时必须按“经营涨跌”与“系统成功/错误”拆分语义，避免把组件库默认的国际涨跌色带入报表。

### 8.3 取数边界

仪表盘、销售、库存、网店等页面包含复合请求和领域级聚合；这类取数应留在页面/领域 hooks。单一列表可由表格 request 适配器接管。全局搜索已经有防抖、AbortController 和迟到请求保护的雏形，应抽成公共 latest-request hook，而不是每个 ProTable 各写一份。

### 8.4 权限与登录墙

当前服务端角色固定为 `viewer / analyst / operator / admin`，并带仓库/渠道/平台 scope；前端写入口按角色隐藏，服务端再次校验。导航目前不按角色过滤，这是因为 12 个模块不是后端下发的 `me.modules`。提示词中的“按 `me.modules[].sort/can_read/can_edit` 渲染”不适用当前接口，除非单独设计并实现新的服务端模块授权能力。

当前匿名/鉴权失败会落成“访客只读”，而不是路由级登录墙。若要收口登录墙，必须作为独立安全变更同时覆盖：首次身份加载态、401 跳转与 return_to、403 禁止访问、页面闪烁、退出登录、开发环境本地直连，以及所有 API 仍由 `requireAppPrincipal()` 强校验。

## 9. 可访问性与响应式风险

1. 大量 7–11px 字号低于常规桌面后台的可读基线，截图中辅助文字明显偏小；
2. 侧栏折叠按钮的 `aria-label` 始终是“收起侧边栏”，展开时语义不正确；
3. 移动菜单按钮没有 `aria-expanded` / `aria-controls`，抽屉打开后没有看到焦点圈定和关闭后的焦点恢复；
4. tab 使用了 `role="tab"`，但普遍缺少 `id`、`aria-controls`、`tabpanel` 与方向键导航；
5. 全局搜索对话框只在输入框上处理 Escape，缺少通用焦点陷阱与焦点恢复；
6. 多个弹层依靠点击遮罩关闭，需检查屏幕阅读器名称、初始焦点和背景不可交互；
7. 字符图标（`⌕`、`♢`、`‹`、`?`）在不同字体和缩放下表现不稳定；
8. 已存在 `:focus-visible` 和 `prefers-reduced-motion`，这是应保留并扩大的基础；
9. 响应式规则数量很多且分散，断点包含 420/560/580/620/680/720/760/860/900/960/980/1180/1200/1320px，存在相互覆盖和回归风险。

进一步静态统计显示，CSS 中有 656 个固定像素字号声明，其中 522 个落在 7–10px；页面主文件有 174 个 `<th>`，但只有 1 处显式 `scope`。根样式后续还引用了未定义的 `--card`、`--ink`、`--ink-2`、`--accent`、`--accent-soft`、`--code-bg` 等变量，相关声明会退回继承值或初始值，应在令牌迁移前先建立“变量必须已定义”的检查。

## 10. 技术债与风险排序

### P0：重构前必须钉住

- `app/page.tsx` 同时承担类型、API、布局、导航和十余业务域；
- 业务模块与 tab 没有 URL 状态，无法深链或刷新还原；
- 缺少统一请求客户端，401/403/网络错误处理不一致；
- 当前“访客只读”不是明确的登录墙；
- 引入 antd/ProComponents 的 React 19、Vinext、RSC、Cloudflare 构建与包体积兼容性尚未验证。

### P1：公共层优先

- 设计令牌不完整、散色散值较多；
- 35+ 张手写表格、多个列设置/多选筛选实现重复；
- 页面加载/错误/空态虽然多数有区分，但没有统一组件契约；
- 断点过多、样式单文件过大、业务样式缺少模块边界；
- 原生输入、弹层与 tab 的键盘/ARIA 行为不完整。

### P2：逐页处理

- 文字图标、静态 badge、无动作帮助入口；
- 格式化函数、筛选器和小卡片散落在超大页面中；
- 一些自定义图表动画与 `prefers-reduced-motion` 的覆盖需逐项验证；
- 列表本地排序与服务端排序边界需要按数据规模重审。

## 11. 阶段二需要用户确认的决策

在写迁移方案或代码前，需要确认以下架构选择：

1. **组件库范围**：
   - 方案 A（当前建议）：先不加依赖，按 Ant Menu 的信息架构与交互规范重构现有应用壳，同时完成 URL、焦点和 token 基础；
   - 方案 B：隔离试验 `antd` 的 `Menu/Drawer/Tooltip`，先验证 React 19、Vinext SSR/水合、Cloudflare 构建、样式顺序和包体积，再决定是否进入主应用；
   - 方案 C：直接引入 `antd + @ant-design/pro-components`，获得 ProTable/ProForm 能力，但依赖、样式、路由假设和迁移面最大，当前不建议未经试验就采用。
2. **路由契约**：先用 query 参数保持单页兼容，还是拆成 `/sales`、`/inventory` 等真实路由。
3. **登录墙排期**：是否与外壳迁移同批交付；如果是，需把匿名只读行为改为明确加载/登录/拒绝状态。
4. **首个试点页面**：建议从导入历史或工作计划列表开始，不以市场 AI、库存备货或大文件导入作为首个试点。
5. **视觉密度**：保留桌面高密度风格，但将正文与控件基线提升到可读字号；是否同时提供 compact/comfortable 两档密度。
