# 固定筛查的公开入口与实际五 Agent 调度

第五十批接通 `POST /api/ai/business-reports` 的显式 `analysisMode: screening-v1`。旧请求保持原分析协议。新请求先创建固定任务，再由工作流队列领取准备租约、完整扫描并保存筛查结果、核验实际模型和工具容量，最后派发三个专业 Agent。独立复核依赖三个专业结果，整合报告依赖独立复核及专业结果，最后等待人工复核。

每次 Agent 微步骤在事务外重建自身读取证明与必要预算；预留调用、保存回执和完成任务时，在短事务核对当前权限、真实任务租约、固定输入及既有账本。固定工作流推进前也核对所有已绑定子任务属于当前报告和正确角色，禁止把其他报告的已完成结果传给后续 Agent。

实际收到的最终模型回答先保存为已知成功回执，再验证完整阅读和引用数值。验证失败可停止任务，但不把已收到结果改为未知、不自动再次调用模型。工具调用只允许当前固定报告、范围和筛查身份，并强制本人角色包的连续读取；该 Agent 的必读预算也必须完整。

公开创建及人工复核使用事务外准备和私有提交回调。报告/复核变更与 HTTP 完成回执、审计同事务；不确定的 processing 请求不自动重做。详情页的准备状态由实际租约、已发布筛查和实际子任务推导，只用于展示，不授予执行资格。

合成全流程使用真实队列、三个实际并发通道、五个独立任务和真实持久证据；模型边界以合成回答替代。这证明协作、数值核验与失败恢复，不证明真实模型经营判断已经合格。最终验证记录见 [候选证据](evidence/ai-business-screening-execution-candidate.json)。
