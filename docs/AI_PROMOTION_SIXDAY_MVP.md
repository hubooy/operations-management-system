# 京东推广深度诊断六天首版候选

## 范围与验收口径

用户确认首份报告固定为京东「志高商用设备旗舰店」2026-09-20 至 2026-09-25，前等长周期为 2026-09-14 至 2026-09-19。09-26 不在首报范围内。首版复用现有网店推广页面、权限、京准通导入事实和 XLSX 写入能力，生成总览、趋势、计划、跟单 SKU、关键词、搜索词、词货、计划关联 SKU、计划关联关键词、搜索词关联 SKU、人工行动建议和来源口径十二张表。HTML 可离线搜索、排序、分页、按结论/行动定位精确对象、沿同一来源行查看关系并导出当前表 CSV；XLSX 的表格数值与 HTML 来源一致，并带标题行、冻结行和筛选。

确定性报告的分析类型为 `deterministic_review_draft`：规则生成待人工复核的判断，不自动修改投放，也不把平台归因额称为店铺净销售、利润或增量效果。可选单模型解读单独标为“AI解读（人工复核）”，只解释已计算对象，必须引用可回查的证据 ID；系统导入批次和店铺归属未对平前禁止派发。用户选择沿用现有默认模型的 65,536 最大输出 Token、按实际计费；本入口仅手动触发且失败不自动重试，不更改全局模型配置。原五阶段候选中的影子库、五 Agent 签发链和额外协议不作为首版依赖。

## 系统接线

- Django 只读 `GET /api/netshop/promotion-diagnostic`：管理员、京东平台、精确店铺复合键和最多 31 天范围；按原始 `NetshopRow` 的已导入推广事实汇总，逐日对平 `NetshopPromotionShopDaily`；逐行归属批次与逐日聚合的发布批次分别核实，披露各自警告数，不误认为两者必须相同；缺日、缺指标、未知分组身份明确返回；八种分组是同一来源行的替代视角或真实关系，不跨表相加；超行数/分组数/响应大小拒绝截断。
- Next 同名 API：沿用应用身份与店铺授权，严格过滤查询参数并代理到 Django reader。
- 推广分析页：仅在目标店铺及 1—7 日已选周期显示“生成当前周期诊断”；前等长周期单独读取，缺失或修订变化时环比留空；切换范围会中止旧请求。来源不完整时只展示缺口，不开放完整报告导出。
- 报告生成器：HTML 和 XLSX 使用同一组表格单元格；来源修订、日期覆盖、主对象分组与关系分组总行数校验失败时拒绝生成。计划按稳定 ID 汇总，未知计划不参加集中度排名；无关键词/搜索词的投放单列，不当作词效果。四类对象按稳定身份显示本期/前期/变化，新增、消失、缺身份或缺基期保留独立状态，不补零制造增幅。
- 可选 `POST /api/netshop/promotion-diagnostic/interpret`：服务端重新读取同一店铺、期间和修订，只选择有界的精确对象证据；先核系统店铺注册与两类已完成、零告警导入批次归属，再复用现有 `analysis-reply` 单模型入口。模型回复必须为有限结构化 JSON，全部证据 ID 在本次白名单内，每项含精确对象引用；数值仍来自确定性表，模型文字与规则分表。原始账户昵称仅作来源信息，不单独当作店铺归属凭据。

## 实际来源的只读预核对

运营管理系统现有导入批次显示 2026-09-20 至 25 六天共 61,311 行，业务日逐日完整。六天合计花费 9,363.22 元、展现 100,460、点击 4,591、平台归因订单行 134、归因总订单金额 105,118.75 元。系统批次绑定京东「志高商用设备旗舰店」，受控店铺注册表将其映射至 shopId 701455；新 reader 还要逐行核对 batch ID、completed 状态、业务日及逐日聚合。来源行中计划 ID/名称、跟单 SKU ID 和五项核心指标均有值；关键词仅在 22.22% 行出现，其空值行占花费约 83.27%，搜索词在 84.99% 行出现。六天可识别计划 27 个、跟单 SKU 581 个、有值关键词 124 个、有值搜索词 7,790 个、关键词×SKU 分组连空值桶共 1,560 个。原始账户昵称与登记登录标签不同，但它只是平台来源字段，不能替代系统导入店铺复合键；报告保留该差异供复核。

运营系统的前等长周期六天为 62,566 行，花费 9,809.37 元、展现 97,094、点击 4,291、归因订单行 151、归因总订单金额 121,753.05 元。十二个日期的正式导入批次均为 completed/零告警，店铺、日期、行数及原文件摘要与系统运行记录匹配；正式推广概览的十二日五项逐日聚合与已导入来源预核对 60/60 差值均为零。新诊断接口正式发布后须以生产 reader 再验精确批次及全分组；不用重新下载平台文件。

## 明确边界与剩余验收

首版暂无同店同日期的品类/SPU 映射、市场、店铺净销售、B 端销售及同比的已验收关联；报告会显示缺口，不补造这些结论。归因窗口成熟度与因果效果未独立核实。61,311 行本地内存读侧演练含三种真实关系约 9.84 MB JSON，低于 12 MiB 响应上限，但不含生产数据库 I/O。

逐项数据可得性见 [六天诊断系统数据缺口](AI_PROMOTION_SIXDAY_DATA_GAPS.md)：B 端销售和京东店铺级概览是真缺采集；SKU/SPU 日数据、主数据、ERP 店铺净销售及市场榜单已有系统来源，当前只是本 MVP 未接线。不要把延期模块或开发接线任务写成让用户重做下载工作流。

先前用现有已导入清单及其留存原始文件生成的离线试用件保存于 `outputs/01a0a909-291e-7c21-bd8b-9a8363c3177f/`，文件名标注“真实来源待身份核验”。它仅是开发期交互与格式核对，不是最终成品或已发布系统的下载回执；本地合同使用 `offline-manifest-v1`，正式新 reader 当前返回 404。离线 HTML 约 5.23 MB，Chrome 本地打开、十二表切换、精确关键词定位→77 条真实关联 SKU、无外网请求通过；XLSX 约 2.03 MB，十二工作表、数值、来源日期与 23,195 行搜索词×SKU 表由独立读取器复核。四类主对象表各自把本期 9,363.22 元和前期 9,809.37 元完整对平，不跨表相加。最终报告必须在系统中读取已导入事实、生成并下载；不再以本地留存 CSV 替代在线验收。后续受控发布不触发新下载、导入或迁移。

定向验证：Django 接口权限、店铺隔离、缺日、聚合差异、响应超限；TS 报告六天日期、对象级比较、新增/消失、关系守恒、精确定位、AI 证据/回包校验、HTML 脚本语法、XLSX 同值、匿名计划防误判；现有 XLSX 读取用例回归及 `vinext build`。截至本文候选状态，生产环境未改变，真实付费模型未调用。

## 本 MVP 受控采用顺序

1. 仅用运营系统内的受控店铺注册表、已完成导入批次、来源行 batch ID、逐日聚合及只读接口核对店铺、日期和五项指标；昵称差异留作来源注记。任何系统内缺失字段如实列入缺口清单，不打开京准通账号页，不新建平台下载/导入任务。重做两期报告与定向测试。
2. 更新到最新主线并固定候选源码，在线预置 Django 应用和 Worker successor；检查当时的 n8n/helper 与导入任务已排空。制作发布前 PostgreSQL 一致性备份，在独立端口完成恢复内容复核，并核对 E 盘归档逐文件摘要。
3. 用已部署的唯一 Worker 生命周期入口进入保留 PostgreSQL 的持久维护。按原受控 `DeployApp`/`HardenAcl`、Worker successor apply、精确退出维护及唯一 `Start` 顺序采用；不改迁移清单、n8n 工作流定义或业务数据。
4. 验 12 组件、Ready/exact_release、启动绑定、守护与既有渠道。再从正式 reader 读取本期和前期两次诊断，量取查询耗时、逐日批次/账户字段覆盖、五项指标、关系分组与修订一致性；页面选择六天、生成、定位对象、沿关系查看、下载 HTML/XLSX，并用独立读取器与正式响应对平。系统批次归属和模型配置均确认后才手动触发一次单模型解读，校验引用和独立 AI 表。
5. 完成发布后备份、复验及 E 盘归档。任一来源、权限、超时、产物或版本门禁失败时保留现场并按原回退流程处理，不把旧离线件冒充在线终验，也不手动补跑下载/导入。
