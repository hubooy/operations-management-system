# 天猫商品日与推广日缺口规划

## 2026-09-09 逐日循环版本（待本机发布）

用户已确认将六店优化为每日查缺并逐日补齐。仓库模板已改为 `领取 helper → A → (B → C → P → N)循环 → M → 完成判断`。下面 2026-09-06 的“一轮一天”是旧版已采用契约；只有新 helper 与六个原 n8n ID 全部受控发布并回读后，才按本节判定生产行为。开发完成不等于已补齐生产数据。

- A 使用 `/plan-backfill`，固定本店注册起始日至启动时上海昨天的范围，选择两类缺口中最早一天。该新入口在旧 helper 返回 404，避免新版工作流误用旧 helper 而产生单日业务动作。
- B/C 仅补所选日的商品缺口，P 核验同日商品覆盖后仅补推广缺口。每次下载和导入仍为单日。全部已覆盖时也经过空 B/C/P，保留 P 的未决活动清单门禁。
- N 使用 `/next-day`，绑定同一 execution ID、店铺键和从 0 开始的 `$runIndex`。只有 C/P 成功后才可进入；重新查同一范围的两类覆盖，确认本轮及此前完成日均已覆盖，再把下一日计划交回 B。缺失未消除、覆盖回退、循环序号过期、跨店、并发、日期漂移均停止。
- 每店每个完整 execution 最多补 14 个日期；从 A 开始 30 分钟后不再开启下一日，当前日的有界节点和 M 收尾允许继续。因此 30 分钟是新增日期预算，不是硬中断计时。共享 helper 排队时间不占本店预算。六店保持原定时及串行门禁。
- 无剩余缺口或达到预算时才进入 M，按原每日/三日规则执行一次或 `not_due` 并关闭本店浏览器、释放 helper。N 未完成时禁止跳到 M。M 返回 `dailyBackfill`，包括完成日期、两类剩余缺口、状态及预算原因；达到预算仍有缺口时，n8n 在 M 收尾后进入显式失败节点，不能发“全部补齐”消息。
- 每次 N 的进度保存为 create-only 的 `outputs/tmall-sycm-cookie-pipeline/backfill-<execution>-<store>-<cycle>.json`，关联各单日计划。它只提供审计，不是导入授权或业务事实源。中断后从 n8n 新完整 execution 的 A 重查权威覆盖，原 P/M 清单继续按原身份恢复，不删除清单，不重放结果未决的业务提交。

验证入口：`node --import tsx --test tests/tmall-daily-backfill.test.ts`；真实 n8n 引擎隔离验证使用 `node tools/test-tmall-backfill-n8n.mjs <已安装n8n包的绝对目录>`。后者创建独立临时 SQLite、用户目录和随机端口，把所有 HTTP 节点绑定本地模拟服务，禁止继承生产数据库变量或调用生产 helper；验证六店多日循环、序号、M 仅一次及预算失败出口。业务入库语义继续由原 C/P/M 的精确批次和覆盖回查保证。

## 状态与范围

2026-09-06 用户要求六店在商品日、推广日下载前先核对缺失时间段，再按日下载。本变更适用于现有六条 n8n 工作流共用的 helper；**已受控采用，商品补缺与推广补缺已有真实成功证据，但整轮和六店端到端验收尚未完成**。不得把代码已上线解释为所有历史缺口已补完。

保持六店 workflow ID、调度、店铺资源隔离、原子协调门禁及 A→B→C→P→M 顺序不变。亿玖/亿用继续使用直连 P/M，其他四店策略不变；M 不是日表现报表，其每日/三日持久节奏不随此次日期规划变更。

## 规划与执行契约

1. A 从当前店铺 `initialStartDate` 到上海昨天读取该店 Django/PostgreSQL 商品日、推广日覆盖；显式恢复范围仍必须位于注册起始日至昨天。读取失败、日期范围不符或覆盖格式损坏时停止，不能当作空库重新下载。
2. 分别计算 `missingProductDates`、`missingPromotionDates`，从二者并集按时间升序选择本轮日期，记录覆盖取证及剩余日期；不是仅查询最大已导入日期，也不是每天固定重下昨天。非连续缺口和跨月缺口逐日列出。
3. 继续保持 helper **每轮最多一个业务日**的现行安全预算。多个缺失日需要后续新的完整 n8n execution，每轮重新读取覆盖继续最早缺口；本变更不新增并发、第二套日调度、循环业务接口或无人授权的自动补跑。若缺口较多，单次定时不会把全部历史一次补完。
4. B/C 只处理所选日期中商品日缺失的部分。商品日已有、推广缺失时，B/C 正常空工作收尾，不重复下载商品文件；P 在下载前重新核验同日商品已覆盖，再只下载缺失推广日。商品缺失、推广已有时，先补商品，P 返回 `skipped / already_covered`。
5. 无任何缺口时不创建商品或推广任务，P 复核覆盖未变化后正常跳过，再进入 M 终态。`already_covered` 表示未产生新的下载/导入，不得作为新批次通知；M 未到期仍必须正常关闭本店浏览器、释放 helper。
6. 尚有活动清单时不能凭覆盖已有就跳过，也不能删除、重置或跨协议接管原任务。旧清单日期与新计划冲突仍失败关闭，需按原店铺、原快照和原任务恢复；本变更不自动作废丽力、拓丰、炊之王的旧推广任务，也不自动消除报表名称冲突。
7. 明确授权的历史重采可以通过既有受控调用的 `forceExistingDates` 能力执行；普通 n8n 日调度不设置该标志。不能把重采作为日常缺失规划的默认回退。

## 采用门禁

隔离验证：66 项针对性测试通过；全量单元测试 1901 通过、0 失败、23 跳过（总计 1924）。全量 lint 0 错误、9 个既有警告，改动文件 lint 无警告；隔离 helper 打包与 `git diff --check` 通过。本机六店公开只读覆盖 API 的规划试算通过；该试算未调用下载、导入或其他 helper 业务端点，不等同于生产试跑或上线验收。

隔离工作树中的相关/全量测试、lint、helper 构建与 diff 检查通过后，创建聚焦提交；本机采用仍需获得当前发布/服务维护授权，检查无在途 owner，以现有 immutable successor 发布流程加载 helper。不得原地改 release、直接调用天猫业务端点或独立导入。通过同一店铺 n8n 的新完整 execution 验证“仅缺推广、全覆盖、存在旧活动清单”与精确落库回查，再核验六店使用同一已采用 helper。运行前发布版本、受控 owner、浏览器收尾和各店 M 节奏门禁保持不变。
